# Lab 07 - DHCP Reservation and IP Address Persistence

## Overview

This lab documents the configuration of a DHCP reservation for the Debian Server on the local network.

The server was originally using the IP address `192.168.1.117`, but after being powered off for an extended period, it received a different address from the DHCP server: `192.168.1.116`.

Because the server is used for network services, monitoring, Apache, Zabbix, and remote administration, keeping a predictable IP address is important.

Instead of forcing a static IP configuration directly on Debian, a DHCP reservation was configured on the network router. This allows Debian to continue using DHCP while the router consistently assigns the same IP address to the server.

---

## Objectives

* Understand the difference between DHCP and static IP configuration.
* Investigate why the server changed from `192.168.1.117` to `192.168.1.116`.
* Identify the network configuration currently being used by Debian.
* Verify the DHCP lease and routing information.
* Test static IP configuration concepts.
* Recover the network connection after configuration changes.
* Configure a DHCP reservation on the router.
* Keep the Debian Server using DHCP while maintaining a predictable IP address.

## The Problem

The Debian Server had previously been using:

```text
192.168.1.117
```

After the server was powered off for approximately one day and started again, the DHCP server assigned:

```text
192.168.1.116
```

The interface showed the new address as a dynamic address.

The routing table also confirmed that the server was using `192.168.1.116` as its DHCP source address:

```text
default via 192.168.1.1 dev wlan0 proto dhcp src 192.168.1.116
192.168.1.0/24 dev wlan0 proto dhcp scope link src 192.168.1.116
```

This demonstrated that the server was not actually configured to permanently retain `192.168.1.117`.

---

## Investigating the Network Configuration

The network interface was inspected with:

```bash
ip addr show wlan0
```

The interface initially showed:

```text
inet 192.168.1.116/24
```

The network configuration file was also checked:

```bash
cat /etc/network/interfaces
```

The original configuration used DHCP:

```text
allow-hotplug wlan0
iface wlan0 inet dhcp
    wpa-ssid Familia_Silva
    wpa-psk SUA_SENHA
```

The server was therefore expected to obtain its IPv4 address dynamically.

---

## Identifying the DHCP Client

The running processes were checked to identify which service was handling DHCP:

```bash
ps aux | grep dhcpcd
```

The output showed that `dhcpcd` was running.

The installed package was also verified:

```bash
dpkg -l | grep dhcpcd
```

The system was using:

```text
dhcpcd-base
```

The DNS configuration also contained evidence that `dhcpcd` was managing the network lease:

```text
# Generated by dhcpcd from wlan0.dhcp, wlan0.dhcp6, wlan0.ra
```

This was important because it explained why manually changing the address did not permanently remove the DHCP-assigned address.

---

## Testing Static IP Configuration

To understand the behavior, the network configuration was temporarily changed from DHCP to static addressing.

The configuration was changed to use:

```text
iface wlan0 inet static
    address 192.168.1.117
    netmask 255.255.255.0
    gateway 192.168.1.1
```

The configuration was checked with:

```bash
ifquery wlan0
```

The command correctly reported the static configuration.

However, the live network interface did not immediately reflect the expected configuration because another DHCP process was still managing the interface.

---

## DHCP and Static Configuration Conflict

After bringing the interface back up, the server temporarily showed two IPv4 addresses:

```text
inet 192.168.1.117/24
inet 192.168.1.116/24 ... dynamic
```

This demonstrated that the static configuration in `/etc/network/interfaces` was not the only configuration affecting the interface.

The DHCP client was still able to maintain the dynamically assigned address.

Attempts were made to remove the dynamic address manually:

```bash
sudo ip addr del 192.168.1.116/24 dev wlan0
```

However, the DHCP client could recreate the address.

This showed why manually manipulating the interface was not an appropriate permanent solution.

---

## Network Recovery

During the investigation, the interface was temporarily brought down while testing the configuration.

This caused the SSH connection to the server to be interrupted.

The interface was restored with:

```bash
sudo ifup wlan0
```

Connectivity was then verified again through the network.

This was an important practical lesson: network configuration changes made over SSH can immediately terminate the remote session if the active interface is modified.

---

## DHCP Reservation

Instead of continuing to fight the DHCP client on Debian, the configuration was changed at the correct point in the network architecture: the DHCP server.

The Zyxel router provides a DHCP reservation table.

The server's MAC address was identified as:

```text
dc:35:f1:b3:9a:1a
```

A reservation was created on the router:

| Parameter   | Value               |
| ----------- | ------------------- |
| MAC Address | `dc:35:f1:b3:9a:1a` |
| Reserved IP | `192.168.1.117`     |

The router was configured to always associate this MAC address with `192.168.1.117`.

---

## Why DHCP Reservation Was Used

A DHCP reservation provides the advantages of both approaches:

### Debian continues using DHCP

The server does not need to manually define:

```text
address
netmask
gateway
```

The router provides this information through DHCP.

### The server receives a predictable address

The router associates the server's MAC address with:

```text
192.168.1.117
```

Therefore, services configured around that address can continue to use the same endpoint.

### Centralized network management

The IP assignment is controlled by the router instead of being manually configured on the server.

This is particularly useful in environments with multiple servers and network devices.

---

## Final Network Design

The intended final configuration is:

```text
                    Local Network
                         |
                  192.168.1.0/24
                         |
                Zyxel Router
                  192.168.1.1
                         |
                 DHCP Reservation
                         |
              MAC: dc:35:f1:b3:9a:1a
                         |
                  192.168.1.117
                         |
                   Debian Server
                       wlan0
                         |
              Zabbix / Apache / SSH
```

The Debian Server remains a DHCP client.

The router is responsible for ensuring that the server receives `192.168.1.117`.

## Final Configuration Concept

The desired Debian configuration is DHCP:

```text
allow-hotplug wlan0
iface wlan0 inet dhcp
    wpa-ssid Familia_Silva
    wpa-psk SUA_SENHA
```

The important part is that the IP persistence is handled by the router rather than by forcing a static address on Debian.

The actual Wi-Fi password is intentionally omitted from this documentation.

## What I Learned

* DHCP addresses are not necessarily permanent.
* A server can receive a different IP after a long period offline.
* `ip addr` can show whether an address is dynamic.
* `ip route` can reveal the DHCP source address and default gateway.
* `dhcpcd` can continue managing an interface even when another network configuration appears to define a static address.
* Changing network configuration remotely over SSH can disconnect the session.
* Manually deleting a DHCP address is not a permanent solution.
* DHCP reservation is a practical way to maintain predictable addresses.
* The DHCP reservation should be configured on the device acting as the DHCP server.
* Keeping the server on DHCP while reserving its address on the router provides centralized network management.
* Stable IP addressing is important for infrastructure services such as Zabbix, Apache, SSH, and other server applications.

## Result

The IP address persistence problem was identified and resolved through a DHCP reservation on the Zyxel router.

The Debian Server can continue using DHCP while the router reserves:

```text
192.168.1.117
```

for its network interface:

```text
dc:35:f1:b3:9a:1a
```

This provides a predictable server address without requiring a manually configured static IP on Debian.
